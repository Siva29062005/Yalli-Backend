# Yalli Backend

Security-first e-commerce API for yalli.in (single seller, INR, India/GST). NestJS 12 modular monolith on
PostgreSQL (Prisma 7), Redis, RabbitMQ. Approved architecture, schema, threat model and roadmap:
`docs/architecture/PROPOSAL.md` (section 20 = approved decisions and deviations). Storefront screenshots: `reference/`.

## Commands
- `npm run check` — the quality gate: prettier, oxlint (type-aware), tsc, unit tests (root Vitest also runs `frontend/src` specs), e2e tests, build, then `check:frontend` (eslint with `--max-warnings 0`, `next build`, frontend tsc). Must pass before finishing any task.
- `npm run test:browser` — every fake-backend Playwright script in one go (mock API + a test build in `frontend/.next-browser-tests` on free ports); needs `PLAYWRIGHT_MODULE` unless Playwright is installed in `frontend/`. `--only a,b`, `--skip-build`.
- `npm run convert:opencart` / `npm run import:images` / `npm run check:launch` — Phase 12 migration tooling (after `npm run build`; see docs/ops/catalogue-migration.md).
- `npm run start:worker` — the background worker (production process); `./scripts/deploy.sh <env> --dry-run` — rehearse a deploy.
- `npm run create:test-admin` — dev-only extra SUPER_ADMIN; needs `NODE_ENV=development` + `ALLOW_TEST_ADMIN=1`; the MFA secret goes to an owner-only temp file, never the terminal.
- `npm test` / `npm run test:e2e` — Vitest (unit `*.spec.ts`, e2e `*.e2e-spec.ts`). Mocks are `vi.fn()`, not `jest.fn()`.
- `npm run seed` / `docker compose --profile tools run --rm seed` — sync roles+permissions, create first SUPER_ADMIN from `BOOTSTRAP_ADMIN_*` (idempotent).
- `./scripts/setup-dev-env.sh` — creates or tops up `.env` (JWT/MFA keys, flags) without overwriting values.
- `./scripts/verify-docker.sh` — end-to-end Docker check (infra, roles, migration, hardened app container).
- `npx prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script` — generate migration SQL (needs `DATABASE_MIGRATION_URL` set to any URL; it does not connect).

## Conventions
- ESM only: relative imports end in `.js`; no `__dirname` (use `import.meta.dirname`). TypeScript strict; no `any` without a documented reason.
- Validation: strict Zod schemas via `@Body({ schema })` — unknown fields are rejected (mass-assignment defence).
- Responses use the envelope `{ success, message, data, meta, timestamp, requestId }`; errors never expose stacks, SQL or framework messages.
- API is under `/api/v1`; infrastructure probes are `/health/live` and `/health/ready`.
- Modules talk through exported services and domain events only, never another module's repository or tables. When the dependency runs the other way, use an inversion point owned by the caller (e.g. `catalog/product-ratings.ts`: the reviews module registers itself as the rating source). Known exception: account export/erasure in `customers/account.service.ts` (one atomic transaction).
- Hardening is configured once in `src/app.setup.ts` so `main.ts` and e2e tests run the same setup.

## Auth and access conventions (Phase 3)
- Every route must declare `@Public()`, `@Authenticated()` or `@RequirePermissions(...)`; the app refuses to boot otherwise. Add `@RequireStepUp()` to sensitive admin routes.
- Authorization data comes from the DB via `AuthorizationService` (cached 60 s; call `invalidate`), never from the JWT. Customer-owned queries filter by `principal.userId`; a foreign id is a 404.
- Request bodies use strict Zod schemas; per-route limits use `@RateLimit(...)`; security events go through `AuditService` (never put secrets in metadata).
- Role changes go through `role-policy.ts` (pure, unit-tested). Add tests for BOTH allowed and denied paths.
- E2E tests (`test/**/*.e2e-spec.ts`) use `createTestApp()` + `Scenario` helpers, a real embedded PostgreSQL and in-memory Redis/notification fakes; give each client a fresh `X-Forwarded-For` (`freshIp()`).

## Commerce conventions (Phase 4)
- Money: integer paise everywhere; the ONLY pricing function is `priceCart` (`src/modules/pricing`), the ONLY current-price rule is `effectivePrice`; SQL listing logic must stay in parity with it.
- Stock changes go through `InventoryService` only (conditional UPDATE + ledger row in one transaction); never write `inventory` directly.
- Guest-or-user routes use `@OptionalAuth()` per METHOD (not on the class when some methods need `@Authenticated`).
- Raw SQL uses `Prisma.sql` tagged templates; dynamic ORDER BY/filters come from whitelisted fragments only.
- Dates in request bodies: `z.iso.datetime({ offset: true })` (Zod `date()` cannot be expressed in the OpenAPI schema).
- Each E2E test FILE gets its own private database (cloned from the migrated template in `test/support/setup-env.ts`); tests inside one file share it, so still scope assertions to rows the test created.

## Payments / orders conventions (Phase 5)
- An order becomes PAID ONLY in `PaymentService.applyProviderPayment` (facts fetched from the provider, amount+currency checked, row-locked). Never mark paid from a request body, redirect or browser callback.
- Order status changes ONLY via `OrderLifecycleService.transition` (state machine + history + outbox). Lock order: ORDER row, then PAYMENT row.
- Refund capacity moves ONLY via `RefundService.requestInTx` (conditional UPDATE on `payments.refunded_minor`); humans need a second approver.
- Unsafe endpoints (checkout, payment start, refund create) require `Idempotency-Key` and run inside `IdempotencyService.run`.
- Domain events go through `OutboxService.add(tx, …)` inside the business transaction; never publish to the broker directly. Consumers wrap work in `MessageDeduplicator.runOnce`.
- Never call an external API inside a DB transaction unless unavoidable; fetch first, then open the transaction.
- Tests: payment tests use `FakeRazorpayApi` (real adapter + real DB). Use `ctx.drainOutbox()` (not a single `relay.tick()`), and `Shop` helpers for flows.

## Phase 6 conventions (shipping, reviews, notifications, analytics, import)
- GST on delivery: `priceCart` apportions the fee over the lines (`apportionExactly`) and taxes each share at the line's rate; orders store it in `order_items.shipping_*`. Invoice and credit-note maths live ONLY in `src/modules/orders/tax-documents.ts` (pure, unit-tested); never compute tax splits elsewhere.
- Credit notes are issued ONLY by `CreditNoteService.issueForRefundInTx` from the `refund.processed` consumer (not inside the refund transaction). Numbers come from `document_counters` (gapless, per financial year). Credit notes are immutable: never add an update path.
- The delivery fee is decided ONLY by `src/modules/shipping/shipping-rules.ts` (via `ShippingService.resolve`); the client sends a method CODE, never a fee. With no active method, shipping is free. Orders snapshot the method.
- Tracking changes go through `ShippingService.applyEventInTx` inside an order-locked transaction (forward-only, append-only events).
- Reviews: verified purchase only (`OrderService.hasReceivedProduct`), plain text (`cleanReviewText`), PENDING until a moderator decides; edits go back to PENDING. Anything public about a reviewer is masked.
- Notifications: account-security emails are best-effort and must never throw; order messages and OTPs must throw so callers retry. Templates are pure (`notification-templates.ts`): escape every dynamic value, never put a token in a subject or a log.
- Analytics: India calendar days, capped ranges, parameterised SQL with fixed ORDER BY fragments. Revenue = orders PAID in the period.
- Catalogue import: validate the WHOLE file first, dry-run by default, DRAFT by default, never overwrite live stock or status, stock only through the ledger (`adjustInTx`).
- Database sessions run in UTC (`PrismaService` sets it): never rely on the server time zone. Keep that regression test.
- E2E: the test body limit is 1 KB (production 100 KB), so an oversized-body test gets 413. Shipping methods are global state: reset them in `beforeEach`. Use unique tracking numbers per order.

## Phase 7 conventions (hardening)
- NEVER use the shared client (`this.prisma`, `inventory.availability()` without `db`, `coupons.findByCode()` without `db`, `audit.record`) inside a `$transaction` callback, or in a method that is handed a `tx`: pass the `tx` (`audit.recordInTx(tx, …)`). A transaction holds one connection; asking for a second deadlocks the pool under load. `test/commerce/pool-starvation.e2e-spec.ts` (pool of 3) must pass for every new transactional flow.
- Stock returns to the shelf only via `restockCommittedInTx` (single-shot). A cancelled order whose refund fails stays `REFUND_PENDING`.
- A staff role may only be assigned to someone with confirmed MFA. MFA verification is limited per ACCOUNT (`MFA_FAIL_LIMIT`), not just per challenge.
- Any new anonymous route must be added to `PUBLIC_ROUTES` in `test/security/route-sweep.e2e-spec.ts` consciously; the sweep fails otherwise.
- Webhooks: the event-id header is not signed; dedupe also on the signed body hash. Refund events are handled as refunds.
- Reports use `ReportingDb` (read-only column-limited role); grant new report columns explicitly in a migration.
- Key rotation: MFA keys via `MFA_RETIRED_KEYS_JSON` + `rotate-mfa-key`; never swap the current key without the retired entry.
- Runbooks and the DR drill live in `docs/ops/`; security review record in `docs/security/phase-7-hardening.md`.

## Phase 9 conventions (launch-blocker fixes; record in docs/security/phase-9-fixes.md)
- 401 codes: the JWT guard's 401 is `ACCESS_TOKEN_INVALID`, the ONLY one a client answers with a refresh; a wrong password/code is a plain `UNAUTHORIZED` (never retried). An unknown/used-up sign-in challenge is `MFA_CHALLENGE_EXPIRED`.
- Sessions: `remember` on login/MFA verify sets `user_sessions.persistent` (cookies with Expires); otherwise browser-session cookies. Staff (any non-CUSTOMER role, `AuthorizationService.hasStaffRole`, uncached) are never persistent and end after `STAFF_SESSION_MAX_HOURS`; granting a non-customer role signs the person out everywhere. Refresh keeps the session's CSRF token. Grace: only a session issued in cookie mode (`user_sessions.cookie_mode`) whose refresh token came from the COOKIE, reused within `REFRESH_REUSE_GRACE_MS`, gets an access token (at most `REFRESH_REUSE_GRACE_MAX`); everything else gets strict reuse detection. Re-granting a role already held is a no-op.
- Refunds a PERSON asked for are never auto-approved (`requestInTx` throws; `refunds_human_approval_chk`). A staff cancel of a paid order only REQUESTS it (PENDING refund in the staff member's name, nothing restocked); `RefundService.recompute` cancels and restocks the order (`OrderLifecycleService.markPaidOrderCancelledInTx`) once that cancel refund is PROCESSED; rejected/failed returns it to where it was. Cancel refund keys are per attempt (`cancel:<orderId>`, then `cancel:<orderId>:<n>`) so a rejected attempt is never reused. A customer's own cancel requests its refund first, then cancels the fulfilment. Fulfilment refuses any order with `cancelledAt`. A partial refund returns the order to its fulfilment state (`statusAfterPartialRefund`), but a cancelled order (`cancelledAt`) never leaves REFUND_PENDING except to REFUNDED.
- Payments: an AUTHORIZED payment reports `authorized` again so the capture is retried; FAILED -> AUTHORIZED is legal while the order is payable. `captureIfAuthorized` claims `payments.capture_started_at` (one attempt at a time, stale after 2 minutes) and applies an already-captured provider payment instead of capturing another (never two captures). An authorization for the wrong amount is a `mismatch`.
- GST documents: invoice numbers `INV/<FY>/<serial>` are taken in the PAID transaction and credit notes `CN/<FY>/<serial>`, both via `takeSerial(tx, …)` (`orders/document-counter.ts`, gapless, max 16 characters). Never derive a document number from the order number.
- `stripTags` returns PLAIN TEXT (it may contain `<`, `&`): every consumer escapes it; never insert it as HTML.
- Consumers de-dupe with `runOnce` (INSERT … ON CONFLICT DO NOTHING) and read through its `tx`.
- Rate limits: production refuses `TRUST_PROXY_HOPS=0`; browser `/api/v1` calls reach the API through CloudFront + ALB (not the Next server). The storefront server's PUBLIC GET requests carry `X-Frontend-Key` (`FRONTEND_SERVER_KEY`, server-only, same value in both apps) and get their own budget.

## Phase 11 conventions (admin console; record in docs/architecture/phase-11-admin.md)
- Paged admin lists call `useClampedPage(meta, page, setPage)` (AdminKit). Every admin screen uses `AdminPage` + `useAdminQuery` + `withStepUp` (no screen has its own sidebar or step-up prompt).
- Variant PATCH: send only changed fields; the server ignores price fields equal to the current value (no `pricing.update`, no price audit). `GET /admin/roles` marks `assignable` (`canAssignRole`): offer only those.
- Refund retry: a FAILED refund becomes a NEW request by the retrier (four-eyes), `refunds.retry_of_id` UNIQUE (one retry each); a cancel refund keeps the cancel key family (`cancel:<order>:<n>`) and is refused once the order is no longer PAID/PROCESSING. `recompute` completes a cancellation only if the order was unshipped when its cancel refund was requested.
- Customer lookup: `POST /admin/customers/search` (never put a searched email/phone in a URL); exact email, VERIFIED phone or order number only, masked contact (`common/utils/mask.ts`), no staff accounts, every search/view audited without the searched value.
- Audit viewer reads through `ReportingDb` (column grant on `audit_logs`, no `user_agent`); periods capped at 92 days.
- CSV exports use `common/utils/csv.ts` (quoted cells, formula prefix neutralised), paise -> rupees with integer maths, India dates, audited `finance.exported`. GSTR-1 layout lives ONLY in `orders/gstr1-export.ts`.
- The refund email is sent on `credit_note.issued` (with the note attached, `credit-note-document.ts`) for invoiced orders, on `refund.processed` otherwise. Email attachments go through `mime.ts` (SES Raw only when attached).
- Warehouses: default always active; no switching off with stock or reservations; thresholds via `InventoryService.setLowStockThreshold` (never write `inventory` elsewhere). Stock rows are created on demand in ACTIVE warehouses (`ensureRowInTx`, `FOR SHARE` on the warehouse); committed goods are restocked to the warehouse they were reserved from.
- Console catalogue import: same service as the CLI; applying needs a dry run of the same bytes+options by the same person in 30 min, once (atomic counter); publish needs products.publish, stock inventory.adjust, update-existing products.update (CLI too); import price changes are audited per variant; failure reasons are safe text (raw errors only in the server log). Console cap 2 MB / 500 products.
- New admin screens: Brands, Import, Finance, Customers, Messages, Audit log (plus the rebuilt Categories). Add every new screen to `ADMIN_SCREENS` (`anyOf`, plus `allOf` when the endpoint requires several permissions), `test-admin-access.mjs`, `test-admin-screens.mjs` and `test-admin-real.mjs`.

## Phase 12 conventions (catalogue and business setup; runbook docs/ops/catalogue-migration.md)
- OpenCart data enters ONLY through files: `npm run convert:opencart` (pure `catalog/import/opencart.ts`: phpMyAdmin JSON export -> import file, paise by string maths, warnings for everything adjusted, `blocking` problems stop it). OpenCart prices of products with a tax class are pre-tax: never import them as GST-inclusive without `--prices-include-gst`. Sale dates travel in the import file (`saleStartsAt`/`saleEndsAt`). No live connection to OpenCart.
- Images from OpenCart: `npm run import:images` reads a LOCAL folder (`image-paths.ts` refuses `..`, absolute paths and links out of it) and uploads through `CatalogAdminService.uploadImage`. Never fetch image URLs (SSRF).
- GSTIN: `common/india/gst.ts` (`checkGstin`: shape, check character, state code; GST state codes live there). The backend refuses an invalid `SELLER_GSTIN` or one from another state than `SELLER_STATE`. `npm run check:launch` (`common/launch-config.ts`) compares both apps' business settings; it names settings, never their values (tested). State names are compared without case.
- Home page: the hero is the owner's banner (`NEXT_PUBLIC_HOME_HERO_IMAGE`, a file in `frontend/public/`) or a real product photo (`ProductImage fit="contain"`), never a stock photo; no product appears twice; the "on sale" row shows only while something is on sale. `ProductImage` passes `preload` (Next 16 deprecates `priority`).

## Phase 13 conventions (infrastructure; plan in docs/ops/deployment-aws.md)
- Images: every upload is re-encoded (`catalog/media/image-processing.ts`, sharp): metadata dropped, ≤2400 px, ≤25 MP input, one image at a time, palette PNGs stay palette (output must stay under `MAX_IMAGE_BYTES`), bombs refused. Test fixtures must be REAL images (make them with sharp), not magic bytes.
- Storage: `STORAGE_DRIVER=local|s3` (`S3Storage`: private bucket, SSE, `If-None-Match` so keys are never overwritten, keys validated like on disk). Production refuses local.
- Processes: API `node dist/main.js` (`BACKGROUND_JOBS_ENABLED=false` in production), worker `node dist/worker.js` (same image, jobs always on), migrations as the `migrate` target; frontend `frontend/Dockerfile` (standalone only when `NEXT_OUTPUT_STANDALONE=1`; `next start` stays for tests).
- Redis failures answer 503 (`EphemeralStoreUnavailable`); callers that treat a cache as optional catch it themselves.
- Deploys: `./scripts/deploy.sh <staging|production> [--dry-run] [--skip-check]` and `--rollback <commit>` (no CI): config in git-ignored `deploy/<env>.env` (plain KEY=value, never executed, never secrets). Images are ARM64 (`DEPLOY_PLATFORM`), ECR tags immutable, a commit's API image is promoted not rebuilt; frontend build args come from `dist/cli/frontend-build-args.js` (same parser as `check:launch`).
- Consumers bind only where background jobs run (`RabbitMqBus` checks `BACKGROUND_JOBS_ENABLED`): the worker in production. Re-encoded images stay under `MAX_IMAGE_BYTES`; production refuses a localhost/http `MEDIA_BASE_URL`.

## Frontend (`frontend/`)
- Next.js 16.4 / React 19.3 / Tailwind 4.3.5 / zustand. This Next version has breaking changes: read `frontend/node_modules/next/dist/docs/` before writing Next code (see `frontend/AGENTS.md`).
- Dev: backend on :3000, frontend with `npm run dev -- --port 3001` (backend `FRONTEND_BASE_URL` defaults to :3001). Next rewrites proxy `/api/v1/*` to `API_INTERNAL_URL` (default `http://127.0.0.1:3000/api/v1`), so the browser stays same-origin.
- Storefront, `/auth/*`, `/account/*` and ALL admin screens use the real API (no demo data; never add demo/fallback data). Admin goes through `AdminAccess` + `admin-session` (staff password + MFA, access token in memory only). Frontend role checks are not an authorization boundary.
- Admin screen pattern: wrap in `AdminPage` (`components/AdminKit.tsx`), load with `useAdminQuery` + `adminList/adminGet` (`lib/admin-api.ts`), mutate through `withStepUp(() => adminPost(...))` from `useAdminSession()` (one shared MFA step-up prompt, then auto-retry). Money typed by staff goes through `rupeesToPaise` (no floats); unsafe endpoints (refund create) send an `Idempotency-Key`. Paginated lists need `adminList` (it keeps `meta`).
- Backend added for the screens: `GET /admin/brands`, `GET /admin/users` (users.manage), `order.orderNumber` on `GET /admin/refunds`, and `permissions` (the caller's own, database-backed) on `GET /me`. Admin screens are verified against a fake backend AND the real app on an isolated database (harness below); the dev Docker `yalli-app` image must be rebuilt to get the new endpoints (README, "Rebuild the Docker app image").
- Admin access in the UI: `lib/admin-access.ts` maps each screen to the permission(s) it needs (match the `@RequirePermissions` of the endpoints it loads); the sidebar, the per-screen gate (`AdminNoAccess`), the landing page and buttons use it (`can('permission')` from `useAdminSession`, which lives in `components/AdminContext.tsx`: import it from there, not from `AdminAccess`, to avoid an import cycle). Hiding is cosmetic; if `/me` sends no permissions nothing is hidden. Gate every new admin screen and its mutating buttons.
- Public policy pages (`/help /shipping /returns /privacy /terms /contact`) share `components/PolicyPage.tsx`; business facts come ONLY from `lib/business.ts` (`NEXT_PUBLIC_BUSINESS_*`, see `frontend/.env.example`), never invented in code. The wording must match real behaviour (7-day return window = `RETURN_WINDOW_DAYS`, payment window, refund rules): change the page when the rule changes. Rules, sources and tax decisions: `docs/policies/store-policies-and-tax.md`. Never claim a discount, free shipping or legal review the shop does not have.
- SEO: pure logic in `lib/seo.ts` (unit-tested), site address only from `NEXT_PUBLIC_BUSINESS_WEBSITE_URL` via `lib/site.ts` (`SITE_URL`, `canonicalFor`; nothing absolute is emitted when it is unset). `app/robots.ts`, `app/sitemap.ts` (dynamic, API failures degrade to static pages), `components/JsonLd.tsx` (escapes `<`). Private areas are noindexed by `PRIVATE_PATHS` (robots) and the `X-Robots-Tag` headers in `next.config.ts`: keep the two lists in step and add any new private route to both. Filtered/search/paged listings are `noindex,follow`. Build with the site address set to run `scripts/test-seo.mjs`.
- Known defects from the frontend review (2026-11-19) and the whole-app review (2026-11-27) are listed in `docs/PENDING.md`; the P0s were fixed in Phase 9, the P1s remain. Check there before touching auth, payments, refunds, checkout or the home page.
- Security in the frontend: CSP and security headers live in `next.config.ts` (add any new third-party script/frame/connect origin there; Razorpay and Turnstile are allowed). Post-login redirects only through `safeNext` (`lib/safe-redirect.ts`). Email-link tokens are read with `useUrlToken` (removed from the URL). Captcha: `components/Captcha.tsx` (`NEXT_PUBLIC_TURNSTILE_SITE_KEY`; single-use tokens, reset after each submit). Each Pay click uses a new `payAttemptKey`. Never run the ROOT Prettier on `frontend/` files (different style).
- Phase 10 storefront rules: ONE `<CartDrawer/>` lives in `app/layout.tsx` (never mount it in a page); cart counts use `cartUnits(cart)`. Categories are server-rendered (`listCategoryTree` in the root layout -> `CategoryProvider initialTree`), revalidated once on mount. A page that may call `notFound()`/`redirect()` must not sit under a route `loading.tsx` (streaming fixes the status at 200): use an explicit `<Suspense>` after the checks (see `components/CatalogLoading.tsx`). Paged account lists use `usePaged` + the API `meta` (never guess from the page size). Dates via `formatIndianDate` are India time. The order view's `returnableUntil` / `returnableQuantity` decide the return buttons. Checkout: orders under `MIN_PAYABLE_MINOR` (₹1) are refused (`ORDER_TOTAL_TOO_LOW`); the quote carries `paymentWindowMinutes`. Sign-out across tabs: `AuthProvider` broadcasts with its tab id (a tab ignores its own message); use `endLocally(path)` when the server already ended the session (sign out everywhere, deletion); only network/5xx `/me` errors are retried. Pages with a fixed filter in their path (`/specials`, `/brands/[slug]`) pass `locked` to `CatalogView` (not clearable, carried into `/catalog/<category>`). Checkout: only the newest quote request may set the quote.
- Phase 10 features: account pages `/account/security` (password, sign out everywhere), `/account/data` (export, delete), phone verification and resend-verification on the profile; `/brands`, `/brands/[slug]`, `/specials` (in `PUBLIC_PATHS` and the sitemap); the contact form (`components/ContactForm.tsx` -> `POST /contact`, module `src/modules/contact`, emailed to `SUPPORT_INBOX_EMAIL` when set, honeypot field `website`; per-IP limit in the controller, per-address cap of 3/hour counted from stored rows AFTER the captcha, so junk requests cannot burn a customer's budget; the support email is not awaited). Contact messages are personal data: included in the account export and erased with the account. Text colours must meet WCAG AA: muted text `#5F6B64`, orange TEXT `#A65500`, dark text on an orange background (never `#8A958E` or `#FF9900` as text on light surfaces). `npm run test:browser` includes `test-a11y.mjs` (axe-core, a pinned dev dependency): no serious/critical violation allowed.
- App-wide error handling lives in `src/app/{error,global-error,not-found}.tsx` and `src/app/admin/error.tsx` (no stack or message is ever shown).
- `npm run check` covers the frontend (lint with no warnings, build, tsc, unit specs). Browser regressions are Playwright scripts in `frontend/scripts/test-*.mjs` against fake backends; run them all with `npm run test:browser` (it picks free ports, so a stale `next start` on 3101 does not matter). The test build sets `NEXT_DIST_DIR=.next-browser-tests` (own `distDir` and `tsconfig.browser-tests.json`); never set it for a real build. Single scripts still take `FRONTEND_URL`, `PLAYWRIGHT_MODULE`. The storefront scripts (catalog, cart, compare-reviews, checkout) also need `node scripts/test-catalog.mjs --mock-api <port>` and a frontend started with `API_INTERNAL_URL=http://127.0.0.1:<port>/api/v1`. Browser-script pitfalls: streamed pages briefly hold a hidden second copy (wait for VISIBLE elements); URL-driven filter boxes change only after navigation (`click()` + `waitForURL`, not `check()`); invoice/credit-note windows open blank first (wait for the document). `test-static-pages.mjs` covers the policy pages and 404; `test-seo.mjs` covers robots, sitemap, canonicals, noindex and structured data (needs a build with `NEXT_PUBLIC_BUSINESS_WEBSITE_URL=https://shop.example.test`).
- Real-backend browser run (opt-in, not in `npm run check`): `npm run serve:browser` boots the real app + embedded PostgreSQL + fixtures + a SUPER_ADMIN with MFA (info file in the OS temp dir; stop by creating `yalli-serve.stop` there), then `frontend/scripts/test-admin-real.mjs` drives every staff screen (browser `/api/v1` calls are redirected to it, so the frontend's baked proxy target is irrelevant). Restart `serve:browser` before every run (TOTP steps and fixtures are single-use). Never point such tests at the dev database: they create shipping methods, coupons and refunds.

## Non-negotiable rules
- Deny by default: every route needs authentication and an explicit permission unless marked public. Never trust client-supplied roles, prices, totals or customer ids; customer-owned data is always queried by the authenticated customer's id (404, not 403, on a miss).
- Money is integer paise plus currency in the database and code; no floating-point arithmetic. The server computes every price, discount, tax and total.
- Login is required to purchase (guest carts allowed, merged on login). Online payment only (Razorpay); no COD.
- PostgreSQL is authoritative for orders, inventory and payments; Redis is cache/rate-limit state only.
- Two DB roles: `yalli_migrator` (DDL, migrations only) and `yalli_app` (DML only, no UPDATE/DELETE on `audit_logs`). The app never receives the migrator URL.
- Never log or return secrets, tokens, passwords or payment data. Secrets come from the environment / AWS Secrets Manager, never from the repo. Do not weaken a security control to make something pass.
- Hand-written SQL (triggers, CHECKs, partial indexes, grants) lives in the migration files and must be kept when regenerating.
- Do not claim tests passed, or a control works, without running it. Do not move to the next phase while security tests fail.
